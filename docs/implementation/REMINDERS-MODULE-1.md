# 模块1：提醒数据契约、持久化与调度核心

本轮分支 `feat/reminders-animation-update`。用户确认按提醒→语音→在线动画顺序分模块实施，每个模块完成后汇报；不自动发布。

## 边界

这是尚未接入界面的主应用内部基础模块，不是已经可用的提醒功能。本轮没有新增Android权限、后台组件或插件数据权限，没有改动插件协议v1的现有允许范围。

本轮交付：

- ReminderDraft：文字、首个时间（epoch毫秒）、固定IANA时区、ONCE/DAILY、每日HH:mm、播报开关（默认关闭）、预留provider/voiceId。当前仅允许system，任意插件组件字符串不能当作语音引擎加载。
- ReminderOwner：由主应用认证结果生成的组件与授权指纹，不接受插件自行填写身份；当前为内部契约。后续新增插件请求必须进入主应用确认/授权流程，不能直接调用save。
- Reminder：稳定ID、版本与随机generation、下次时间；每次保存生成新generation，取消后重建同ID也不会接受旧投递回调。
- ReminderStore：JSON schema1，最多200条，每条1000个UTF-16字符，文件2MiB上限；共享文件锁、临时文件fsync和原子替换。损坏或未知版本保留原文件并报错，不静默重置。主应用未来应传入noBackupFilesDir下专用路径，在IO线程使用。
- ReminderCoordinator：保存、查询、取消、撤销授权、取到期项、重新安排最近唤醒及投递确认；回调失效、身份检查和修改在同一存储锁内串行。通知投递失败抛错时不消费提醒。

## 调度约定

持久化数据为唯一事实来源；ReminderWakeup只是可重建的系统调度端口。模块2实现AlarmManager适配、接收器和通知，不使用长期驻留服务轮询。

调用save/cancel/revoke后及应用启动、重启、系统时间改变时必须调用reconcile，并检查当前授权。持久化成功后系统调度失败需显示“待恢复调度”，不得向用户宣称提醒已经正常生效。端口接收null取消旧唤醒，否则替换唯一最近唤醒。

DAILY按用户选择的固定时区、当地时间计算，不按24小时累加。夏令时不存在的时间顺延，重叠时间选较早偏移，当地每天只处理一次。切换设备时区不隐式改变用户选择的时区；模块2需在界面明确展示。补处理最多一项，不批量播放过去几天的提醒；过期通知/错过提醒的具体展现留模块2。

投递端用deliver重新核对授权和回调版本；同步post不得重入仓库。进程在通知成功、确认落盘前被杀可能导致重试，因此通知需采用稳定ID与onlyAlertOnce；不承诺跨崩溃恰好播报一次。语音播放不应阻塞持久化锁，模块3单独协调。

## 后续接入点

1. 模块2：时间选择界面、宿主确认、便签与提醒关联、AlarmManager、通知权限、重启恢复、插件停用/卸载/更新的撤销、错过提醒处理。避免将插件的表单字符串直接用作可信身份。
2. 模块3：系统TTS投递、停止与音频焦点、独立语音接口；本轮字段只是预留，不代表已实现音色插件。
3. 模块4：在线动画目录、多选安装与失败重试，与reminders包独立，避免交叉修改。

## 验证

ReminderTest覆盖一次性提醒、完成状态落盘、旧回调、取消重建、授权隔离、每日补处理、夏令时、损坏文件、并发仓库写入、投递失败重试和取消与投递的顺序。不将JVM测试当作Android后台到点提醒验收。

最终验证：178项主应用JVM测试（新增提醒12项）、Android lint（0错误）、13项Python测试和Ruff检查通过。新增12项提醒测试在CPU负载下重复3轮全部通过。没有运行Android设备到点通知验收，也没有发布或推送。
